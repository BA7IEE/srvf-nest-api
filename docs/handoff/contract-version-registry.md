# 契约版本回执登记表(contract version registry)

> 合同 §16.1 第 ⑤ 条:「App、Admin、worker、管理后台和手机端支持**同一 contract version**」。
>
> 后端能自证的只有**它自己**那一版(`pnpm cutover:check` 的 5a:`package.json` / `apply-swagger.ts` /
> `openapi.json` 三处一致)。另外四端在**别的仓库、别的部署** —— 它们编译时用的是哪一版,
> 后端**看不见**。这张表就是那四端**回执的落点**:本仓唯一能做的,是把「无从核对」变成「可核对」。

## 0. 这张表不会让 5b 变绿

⚠️ **填满这张表也**不会**让 `cutover:check` 的 5b 出现 ✅。**

5b 是 **B 类(机器可查·人判定)**。机器读得到这张表、算得出谁不一致,但**验不了表里的话是不是真的** ——
它是别的仓库的人写下的证词,不是本仓可复算的事实。所以 5b 恒为「⏸ 待维护者确认」,
由维护者看着这张表**自己**做那个判断。这不是保守,是结构性的:
`scripts/cutover-check.ts` 的 `eviSub()` 硬编码 `verdict: 'pending'`,`renderVerdict()` 只在 `kind === 'A'`
时才可能吐 ✅ —— **把 5b 渲染成绿在语法上不可表达**。

这张表改变的是 ⏸ 的**内容**:从「本仓看不见」(死路)变成「这四端里 X 还没回执、Y 报的版本对不上」(工作清单)。

## 1. 机器对这张表做什么

`scripts/cutover-check.ts` 的 5b 每次运行都会:

1. 把每行声明的版本与后端当前版本比对,**点名谁不一致**;
2. 列出**从未回执**的端;
3. 表**不存在 / 被清空 / 少了合同点名的某一端 / 表头被改坏**时当场说出来
   —— 空表恒「零不一致」,那是空绿,必须看得见。

机器**不会**替你判断「五端是否已对齐」。

## 2. 两个哨兵值(不要在本表里写版本号)

| 填什么 | 含义 |
|---|---|
| `未回执` | 该端从未提供过取证。初始状态。 |
| `同后端` | 该端与后端**同仓同构建**,结构上不可能不一致,无需回执。 |
| `x.y.z`(具体版本号) | 该端**实际回执**的契约版本。 |

> 🔴 **除了「实际回执」那一格,本表任何地方都不要写后端的版本号。**
> 后端版本的真源只有三处(`package.json#version` / `apply-swagger.ts#setVersion` /
> `openapi.json#info.version`),多写一处就是**第四处版本声明** —— 它会随发版静默过期,
> 而本表恰恰是用来发现「谁过期了」的。哨兵值由机器在读表时解析成后端当前版本。

## 3. 各端怎么取到自己的版本

各端引入的客户端产物(`docs/handoff/clients/<surface>/{client,types}.ts`)头部带一行:

```
// contractVersion: x.y.z
```

在自己仓里 `grep contractVersion` 即可 —— **不需要后端配合、不需要联网、不需要后端已部署**。
该戳派生自 `docs/handoff/openapi.json` 的 `info.version`,并被 client 的 `inputDigest` 覆盖:
契约改了而 client 没重新生成,`pnpm docs:feclient:check` 当场红 ⇒ **戳不可能与真源脱节**。

## 4. 登记表

| 端 | 所用契约版本 | 取证方式 | 填报日期 | 填报人 |
|---|---|---|---|---|
| App | 未回执 | — | — | — |
| Admin | 未回执 | — | — | — |
| worker | 同后端 | 同仓同构建:worker 与 HTTP 进程出自本仓同一次构建,不存在独立的契约版本 | — | — |
| 管理后台 | 未回执 | — | — | — |
| 手机端 | 未回执 | — | — | — |

> 「端」列的五个名字**逐字取自合同 §16.1 ⑤**,不得增删改 —— 判据按这五个名字查行,
> 少一行会被当场点出来(防止「删掉填不出的那行」把缺口洗掉)。
> 若其中两个名字实际是**同一个部署**(例如 Admin 与管理后台),不要合并行,
> 在「取证方式」里写明「同 X 行」,让合同原文与部署现实的差异**留在台账上**。

## 5. 尚未接通的一环(登记为待办,本刀不做)

- **(a) 运行时版本端点** —— 让生产上的后端自报它正在提供哪一版契约,补上「部署期轴」
  (四端可以全编译在同一版,而生产还跑着上一版)。本刀未做:它要动 `src/`,
  会翻 `docs/ai-harness/ROUTE_AUTHZ.md` 的 digest(红区,需 CI 环境审批),
  而其价值要等 (c) 落地才兑现。
- **(c) 各端 CI 自查** —— 各前端仓在自己 CI 里比对「我引入的客户端戳」与「后端 live 版本」,
  不一致即红。**这要改别的仓库,不在本仓职权内**,由维护者线下推动。
