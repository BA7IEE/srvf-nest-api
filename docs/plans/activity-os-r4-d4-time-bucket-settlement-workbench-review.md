# Activity OS Release 4 / D4：Time Bucket 与结算工作台评审

> **状态（2026-09-12）**：候选方案 A，待维护者确认；不是已批准的实施合同。本轮只合并起草本评审、[精确实施计划](activity-os-r4-d4-time-bucket-settlement-workbench-implementation-plan.md)和 D3 台账更正，验证后提交、推送、创建 docs-only PR；不合并、不实施、不操作数据库、不启用 Gate。

## 1. 这一步解决什么

D3 已能把一段真实参与时间认定成四种分类，但还没有给负责人整理、检查和提交分类结算的工作台。D4 要把“逐段认定”汇成“某次结算、某个参与身份、某个类别”的不可变结果，并把理由、来源和政策版本一并冻结。

推荐方案 A：开放最小 Human App 工作台，复用现有参与事实和 D3 认定；增加分类草稿与正式版本的桶，显式选择新分类提交路径。旧结算入口、旧小时数和贡献分完全保持原样。D4 的“正式版本”仅指已提交给既有审核流程的冻结材料，不表示已入账或已开证明。

不做这一步，后续账本只能再次临时拼接参与段与政策；做错则可能重复计时、用新政策改写历史，或者把未审核结果当作正式服务时长。回退方式是停用新入口并回退应用接线，保留所有新旧数据；不删表、不清理业务历史。

## 4. 数据合同与体验

拟新增四个模型：ActivitySettlementTimeRevision、ParticipantSettlementTimeBucket、ParticipantSettlementTimeBucketSource、ActivitySettlementTimeCommandReceipt；在现有 D3 revision 上增加可空草稿证明锚。模型、字段、同链约束、哈希域、锁序及回放要求以[精确计划 §3–§6](activity-os-r4-d4-time-bucket-settlement-workbench-implementation-plan.md#3-完整数据合同)为候选合同。

工作台依次支持查看来源和阻塞项、人工或自动认定、生成分类草稿、查看四类结果及理由、显式提交。缺失认定、源段变更、封印过期、跨段重叠、政策混合均显示明确原因；不能把错误吞成空列表或零时长。已提交版本可以按当前查看权限读取历史来源，不用今天的政策重算。

没有有效段的参与身份可显示四个零桶，政策指针为空且注明“无有效参与段”；存在开放段、待决事实或应认未认的有效段不能冒充此情况。空桶不产生正式志愿服务证明。前端页面不在本仓实施范围，交接文档只登记后端能力和缺口，不写“页面已上线”。

## 5. 备选与取舍

- A（推荐）：一次交付受控认定、分类桶和显式提交闭环；兼容旧入口。代价是需要新增迁移及 D3 窄合同扩展，并保守阻塞混合政策。
- B：仅对已 committed 段做只读分类汇总。改动较小，但无法完成提交前工作台，因此不能把它标记为 D4 完成。
- C：直接把旧小时数分类或在旧提交流程全量启用新规则。缺少来源证明且影响旧合同，不推荐，也不在候选实施清单内。

精确计划共列 101 个未来路径，包含旧迁移测试、契约生成物及派生台账，不是 101 个业务代码文件。当前 docs-only PR 始终只有 7 个文档；清单不构成预授权。
