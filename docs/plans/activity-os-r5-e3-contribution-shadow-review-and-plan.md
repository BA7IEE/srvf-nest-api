## 1. 结论与不变边界

E3 必须让同一条可比较的参与事实同时经过旧 `ContributionRule` 计算和 E1 `ContributionPolicyVersion` evaluator，留下可复核的差异清单。E3 **只观察**：旧考勤预填仍是正式输入；不回写新分值，不改现有结算、`ParticipationLedgerEntry`、每日封顶、Correction、统计、发布或历史记录。E4 才接结算，E5 才在独立窗口切换并使旧规则只读；E3 通过不能代替 E4／E5 的授权。

**推荐方案 A：先锁比较合同，再接受控 shadow 与不可变证据。** 第一刀用纯函数和固定夹具证明边界／分类／重放；第二刀只在已签映射、同一事实输入和受控开关同时成立时，挂到旧预填链旁边，保持旧结果唯一对外。两刀均为独立 PR，第二刀不因第一刀合入而自动获批。只有真实目标已确认、来源规则和映射逐项签字、同链事实可得时，才能另行申请真实对账；系统尚未上线时，固定夹具对照只证明能力，不能登记为真实存量“差异归零”。

## 3. 推荐比较合同（待业务拍板）

1. 比较单位是一条明确的同活动、同成员、同考勤记录或同一受控夹具事实；固定旧规则 ID／来源指纹、E1 policy/version/hash/evaluator、映射签字版本、事实锚点及发生时间。没有一一对应锚点不比较，不用活动标题或姓名拼链。
2. 旧侧调用现有计算器／等价无副作用适配，保留无匹配 0、阈值 `<=`、`pointsAbove ?? pointsBelow` 和重复 ACTIVE pair 失败语义。新侧调用 E1 纯 evaluator。不得把新侧的 `defaultResult` 擅自解释为旧侧的“无规则 0”。
3. 只有已签的活动类型→四类时长、旧角色→新角色、取数来源、精度／舍入、`defaultResult`／zero 语义和有效时间全部齐全，才判为 `comparable`。G04／G05 默认 hold，G13 的 zero 单独签字；其余未签类型同样 hold。
4. 结果至少区分 `equal`、`points_mismatch`、`legacy_rule_missing`、`policy_version_missing_or_unapproved`、`mapping_hold`、`input_source_mismatch`、`precision_boundary`、`source_drift`、`duplicate_active_pair`、`evaluation_error`。`not_comparable` 汇总不能混入 mismatch 或 equal。错误不得改旧结果或被静默吞掉；shadow 自身故障要形成脱敏诊断并按批准的故障预算处理。
5. 差异判断使用统一的百分位定点表示（旧 Decimal(5,2) 与新字符串点数），逐条保留两侧原值和解释，但不得把比较过程写入正式账本。需要给出总体、逐类型／角色、边界档、缺失与错误分桶；“差异归零”只对有真实来源且完整覆盖的 comparable 集合有意义。

## 4. 证据、权限和留存的三问

业务用途是为 E4／E5 提供可复核的差异治理证据，不是再造正式分数。推荐将每次比较的运行批次、精确版本／来源指纹、脱敏事实锚点、两侧点数、分类和异常码写成**只追加、不可覆盖**的受限证据；不保存姓名、手机号、证件号、原始备注或完整个人资料。可见面推荐仅显式 GLOBAL Human 授权的复核角色，内建角色零默认授予；具体权限码、查询入口、掩码和审计须在实施前单独评审。业务证据不设自动删除或 cron 清理；保留期限与退队后的可见性需维护者明确签字，不能先占位后补。若证据模型、字段或权限未签，本阶段只能做隔离夹具报告，不得把生产 shadow 改成无痕日志。

## 9. E3-1 离线比较器交付边界

E3-1 的输入全部由调用方显式提供：夹具事实锚点、同源旧小时与新秒数、签字映射版本、旧规则快照与来源指纹、已批准政策版本和 definition hash。比较器不查库、不取“最新版”、不写正式账本，也不持久化差异。`equal`／`points_mismatch` 才进入可比较分母；未签映射、角色／类别缺失、来源不同、精度边界、版本／来源漂移、重复 pair 和求值错误均单独分桶。旧小时严格按两位小数换算为 36 秒单位；相差至多 18 秒记为精度边界，更大差异记为来源不一致。签字输入在本轮仅是固定夹具证明，**不是** 31 个真实类型的签字，也不是运行时可信采集链。

E3-1 只校验调用方提供的旧来源指纹 `expected`／`observed` 相等；它不负责从数据库快照独立重算该指纹。E3-2 若推进，必须在属主查询和同事务事实锚点上重新证明来源真实性、规则状态及版本批准，不能拿 E3-1 的夹具布尔值当生产授权。当前无真实目标或真实数据，不能宣称差异归零。

## 15. 既有考勤审计的证据边界补查（仅评审，不实施）

`AttendancesService.submit` 与带 records 的 `edit` 已在旧业务事务内写 `attendance-sheet.submit`／`attendance-sheet.edit` 审计；`after` 含 Sheet 与 Record 快照，审计写失败沿既有合同回滚业务事务。因此，这两类**成功提交**可以用既有审计定位候选旧事实，且不能把“审计存在”误当成 shadow 已尝试。`edit` 不带 records 的分支另有 `edit-no-records` 审计，不能混入逐条贡献值对照分母。

这份审计**不足以单独承担 E3-2 不可变证据**：快照包含 `note` 等敏感原文，现有审计查询会返回完整 `context`，读取范围也不是 E3-2 专用复核面；服务层不提供审计修改／删除方法，但仓内已落 migration 未见针对 `audit_logs` 的数据库级禁 UPDATE／DELETE 触发器。成功旧写的审计还没有签字映射版本、当时的 shadow 开关、对比尝试／结果／失败分类和重放键，不能靠事后猜测宣称“每次 shadow 尝试都有证据”或“真实差异归零”。这些结论是**仓内代码与 migration 的只读核查**，不是生产数据库审计。

后续候选设计只能把旧审计当作受控内部定位线索，不复制其敏感快照到新收据，也不直接开放通用审计 context 作为 E3-2 读面。若要满足 §11 的双重承诺，须另行评审最小化、只追加且数据库可验证的对比／失败收据，以及成功旧写与缺失收据的可核对锚点；必须说明 shadow 开关何时固定、失败发生在提交前还是提交后、如何发现并安全重试缺口。若另加同事务 intent，其写失败会影响旧写；若仅事后 best-effort 写收据，其失败又可能不留痕——两条路都不能在未设计、未验证前称为完成。审计访问面、保留／退队处理及模型字段仍待业务负责人签字；31 类真实映射保持 `hold`。

## 16. E3-2 独立证据链精确设计草案（2026-09-27；仅文档）

维护者本轮确认**证据角色分离**：旧考勤审计只用于内部定位已成功提交的旧写；E3-2 的尝试、比较结果和失败必须由独立、最小化、不可变收据证明。这里的“不可变”要求数据库层拒绝收据 UPDATE／DELETE／TRUNCATE，并通过非空库迁移与直接 SQL 负例验证；仅靠 Service 不暴露修改接口不够。下列是待签的数据合同，**不是**建表、接线或查询真实业务库的许可。

**事务取舍已确认（2026-09-27）**：旧业务事务先按既有合同提交，之后独立写入 E3 收据；新收据失败不得回滚已提交的旧业务。两次提交之间的缺口是明确接受的风险，须逐项人工核对并保留未决状态；缺口未闭合不得宣称证据完整或差异归零。此确认只锁定取舍，不批准审计元数据、收据模型、人工核对工具或运行时实施。

### 16.1 可证明的范围与未闭合缺口

1. `off` 是默认值，旧 submit／带 records 的 edit 不产生 E3 收据，也不改变旧正式值、旧审计或事务边界。无 records 的 edit 不进入逐条比较分母。现有 31 类真实映射仍全部 `hold`；固定夹具只验证比较器，不能伪称真实差异归零。
2. 候选“应比较集合”只能由**成功旧写的审计定位锚点 + 当次已固定的 shadow 资格**组成。现有审计没有当次开关、签字映射版本或可比较事实；事后读取当前配置会发生漂移。因此须另行决定是否在既有必写审计的最小元数据中固定资格标记、映射版本和不含个人原文的事实键。该标记只是缺口核对线索，不充当不可变比较收据；审计元数据变更本身仍须评审其旧事务失败、隐私和读面影响。
3. **已选事务后独立收据**：不在旧业务事务内强制写新收据；进程崩溃或数据库故障会形成空窗。资格锚点与独立收据的人工核对尚未设计定案；在锚点未获批准、完整性不可验证或缺口处理机制未验收前，不可宣称“每次 shadow 尝试都有证据”，也不得开启真实 shadow。不得用同步等待新收据成功来暗中重新耦合旧请求的成功条件。
4. 若业务方要求**数据库级证明所有符合资格的旧写都必有收据**，单靠现有可改的旧审计定位线索不满足；必须重新评审同事务持久资格锚点及其对旧业务可用性的影响，或收窄承诺。不得把“日志里没看到失败”当作完整性证明。

## 17. 资格锚点与旧审计形状冲突的补充评审（仅设计）

只读核对发现 `test/e2e/attendances-audit-characterization.e2e-spec.ts` 对 submit 和带 records 的 edit 使用 `toEqual` 精确锁定审计 `extra` 的四字段形状；无 records 的 edit 另锁为三字段。§16 的“在既有审计 `extra` 添加资格标记”会直接改变这些历史断言，按 `AGENTS.md` 的测试纪律属于**行为契约变更**，不能作为默认实施细节，也不能为了绿灯放宽断言。维护者已确认下述**方案 A 作为资格锚点的设计方向**；这只替换 §16 的审计元数据候选，不批准实施或真实业务查询。

### 17.1 方案 A（设计方向已确认）：全量旧写作为保守核对候选

在一个预先记录起止、版本与操作人的受控观察窗口内，只按既有审计的 `event/resourceId/id` 枚举成功旧 submit 和带 records 的 edit；`edit-no-records` 明确排除。**不更改旧审计字段、旧事务、旧响应或旧 E2E 断言**。新收据独立引用审计 ID 与已核对的业务事实锚点；对每条候选给出“有开始及终态收据／缺开始／缺终态／经人工签字判不适用”四类结论。所有缺口保留原始编号和人工处置记录，不以查询去重、覆盖收据或删除旧事实消账。

本方案会把窗口内实际处于 `off`、未签映射或本就不可比较的旧写也列为候选，**允许多报待核对，不允许漏报后伪称完整**。人工“不适用”须有当次配置／版本及事实依据，不能事后读取当前开关倒填；若证据不足，保持未决。旧审计没有数据库级不可变守卫，所以它只能提供**当前可见旧写的保守定位**，不能单独证明“全部历史旧写未被篡改”。新收据本身仍须独立不可变；若维护者要求数据库级完整性证明，方案 A 不满足，须另评同事务持久资格锚点及旧业务可用性代价。系统尚未上线、无真实样本时只可用隔离夹具演示核对方法，不给出真实覆盖率。

### 17.2 方案 B：改变旧审计合同

在既有审计 `extra` 加当次资格元数据可缩小人工候选分母，但会改变精确锁定的旧审计形状和通用审计读面，且该审计仍非数据库级不可变证据。此方案需维护者**明确批准行为契约变更**，逐条评审隐私、访问范围、旧请求失败方式和全部受影响断言；不能把改测试说成“夹具适配”。它也不自动消除事务后收据空窗。

已确认选择方案 A，方案 B 仅作为被比较的备选保留，不能在实施时自行切换。下一步仍须冻结受控窗口定义、人工“不适用”证据、独立收据字段与访问／留存、完整写集和 D 档 SQL；本次确认**不等于授权实施**。方案 A 保留 §16 已确认的“旧事务先提交、收据后写、缺口人工核对”，不允许把 E3-1 固定夹具或 31 类未签映射冒充真实对账。

### 18.1 已锁定行为与数据流

1. `off` 默认且旧路径零新增业务副作用；旧 submit／带 records 的 edit 在原事务内提交，旧值、响应和精确锁定的审计 `extra` 不变。无 records 的 edit 不进入候选集合。不得向旧事务塞入新收据，也不得为 E3-2 放宽旧 E2E 断言。
2. 受控观察窗口预先登记起止、操作者、版本和配置证据；只用当前可见的成功旧写审计 `event/resourceId/id` 枚举保守候选。它是定位线索，既不能证明全部历史写未被篡改，也不能单独证明当次 shadow 资格。候选可多报，不可因当前配置不符而静默剔除；人工“不适用”须有当次证据和签字，否则保留未决。
3. 旧事务提交后，以已提交事实及签字版本／来源指纹构造确定性重放键，先独立追加最小化开始收据，再做同链比较并追加结果或失败收据。收据失败不回滚旧提交、不改旧响应；旧审计候选无开始收据和开始后无终态收据分开列为缺口。重放只能读取既有终态或追加可追溯的后续处置，不覆盖、删除原收据；并发互斥与唯一键须由数据库约束及测试证明。
4. 31 个真实类型继续全部 `hold`。固定夹具仅可证明机制；未签映射、旧事实／新政策不同源、版本漂移或缺少当次资格证据均归 `hold`／未决，不进入相等分母。不得声称真实差异归零或 E3-2 完成。

### 21.2 SQL 守卫的确定性合同（未来第 133 条，不是已签 SQL）

1. 先为既有 `AttendanceSheet(id,activityId)`、`AttendanceRecord(id,sheetId,memberId)`、`ActivityContributionPolicySelectionItem(id,selectionRevisionId,activityId)` 建复合唯一键，再建五表及复合 FK；旧行不更新、回填或删除。所有新增引用均 `ON DELETE/UPDATE RESTRICT`，不得借 `CASCADE` 清业务证据。实施前必须证明非空隔离库建索引可行、历史同名索引不存在且锁等待受控；迁移失败整体回滚，不改历史 132 条 SQL。
2. Window INSERT 守卫用数据库 `clock_timestamp()` 拒绝 `startsAt <= 当前时刻` 的事后登记；`CHECK(startsAt < endsAt)`，`EXCLUDE USING gist (tstzrange(startsAt,endsAt,'[)') WITH &&)` 拒绝并发重叠。窗口没有取消／删除状态；登记错误不能靠改旧行纠正，只能在未开始且另行审批的后续设计中另建处理机制。D1 不提供该机制。
3. Attempt INSERT 守卫读取并锁定精确 `audit_logs`、Sheet 与 Window：审计 `success=true`、`resourceType='attendance_sheet'`、`resourceId=sheetId`，且 `(event,context.extra.operation)` 仅为 `(attendance-sheet.submit,submit)` 或 `(attendance-sheet.edit,edit)`；审计 `createdAt` 必须处于窗口 `[startsAt,endsAt)`。从审计 `context.after.sheet.version` 与 `context.after.records[*].id` 只读核验当次版本及正数记录数，拒绝 `edit-no-records`、缺字段、重复 ID 和类型错误；不将 `note` 或完整 `context` 复制到新表。`auditLogId` 与 `replayKey` 唯一冲突时只能读取已存在的精确同键收据，不得覆盖。
4. Comparison INSERT 先锁所属 Attempt，再核对无 Terminal；审计 `after.records` 必须包含该 `recordId` 且 `memberId` 与新行一致。复合 FK 固定 record→sheet→activity、选择 Item→revision→activity；触发器另核对 Item 的 `policyId/versionId/definitionHash/evaluatorVersion` 与 Comparison 四元组一致。可空锚点用“全空或全具备” CHECK，不能利用 PostgreSQL 复合 FK 遇 NULL 自动跳过而产生半链。守卫还须拒绝超出预期的第 `expectedRecordCount+1` 条。
5. Terminal 与 Comparison 都先锁同一 Attempt 行（同一锁序）；Terminal INSERT 的事务内定向查询逐条核对总数、四分桶、`comparable` 与分类。Terminal 存在后 Comparison INSERT 一律拒绝；Terminal `(attemptId)` 唯一，失败重放不改旧行。Disposition INSERT 锁同候选最新前驱并验证连续修订、同窗口／审计／attempt，防并发两个 revision＝N＋1；若新候选尚无前驱，仅允许 revision＝1。锁序、是否需要 deferred constraint trigger 和查询预算必须在实际 SQL 与隔离并发 E2E 中证明，不能凭本稿认定已通过。
6. 五表均设数据库级 UPDATE／DELETE 拒绝触发器及 TRUNCATE 拒绝触发器；应用层无豁免开关。由于旧 `audit_logs.context` 没有数据库级禁 UPDATE，收据只能证明自身不可变与插入时的锚点校验；复核时旧审计内容／已提交事实若漂移，必须显式报 `source_drift`，不能宣称全部历史旧写不可篡改。测试夹具临时禁用触发器只准在获批隔离库、同一受控事务内验证并恢复，生产不提供此路径。
