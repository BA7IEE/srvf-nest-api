## 4. 仪器自证(DoD 4)

读数在报出来之前先自证。本仓已有的教训是「**仪器撒谎时读数恰好印证预期**」,
所以以下四条任何一条不成立,上面的读数都不算数。

### 4.1 锁是不是真的加上了

| 判据 | 期望 | 实测 | 结论 |
| --- | --- | --- | --- |
| advisory 持锁数(`pg_locks`) | 200 | 200 | ✅ |
| 集合**外**的 advisory 键仍空闲 | 可立即取到 | 可取到 | ✅ |
| 集合**内**的行 `FOR UPDATE NOWAIT` | 必须失败 | 失败 | ✅ |
| 集合**外**的行 `FOR UPDATE NOWAIT` | 必须成功 | 成功 | ✅ |

第三、四行是一对,专门守「`SELECT 'lit' FROM t … FOR SHARE` 静默不加锁」那个本仓踩过的坑:
写得像加锁不等于加了锁。只验「里面锁住了」的话,一个恒失败的探针也能报绿。

查询计划证明取锁在 Sort 之上(取锁顺序确实跟随 `ORDER BY`):

```
LockRows  (cost=0.29..744.47 rows=10000 width=36)
  ->  Index Scan using probe_day_state_..._pkey on probe_day_state_... d
```

② 段的 version 比对是**真比对**:baseline 不符即抛错终止该轮,否则这一段等于空跑一条 SELECT。

### 4.2 空载基线与反向读数(DoD 4 的两条)

| 对照 | n | P50 | P95 | P99 |
| --- | --- | --- | --- | --- |
| **空载**(同一事务框架,零 lock、零行锁) | 57 | 0.8 | 1.1 | 2.6 |
| **10000 有载整事务** | 57 | 171.8 | 197.7 | 286.8 |
| 10000 一次取锁 ①段 | 57 | 13.8 | 16.0 | 16.5 |
| **10000 拆 2×5000 顺序取锁 ①段合计** | 57 | 15.3 | 18.2 | 33.0 |
| 独立 5000 档 ①段 | 57 | 6.8 | 7.6 | 7.7 |
| 10000 拆 2×5000 整事务 | 57 | 185.7 | 250.3 | 263.5 |

- **空载判据**:有载 P50 / 空载 P50 = **214.7×**。事务框架本身的开销(约 0.8 ms)在万人读数里
  可以忽略,读数测的确实是锁与写,不是框架。
- **剂量-反应判据**:10000 一次取锁 P50 = 13.8 ms,其一半 = 6.9 ms;独立跑的 5000 档 ①段
  P50 = 6.8 ms,**比值 0.99**。取锁耗时随人数线性,计时器对规模有反应而不是常数。
- **拆分判据**:同样锁 10000 个键,拆成 2 段顺序取合计 15.3 ms vs 一次取满 13.8 ms ——
  多出的约 1.5 ms 是多一次往返与多一次语句解析,方向与量级都符合预期;拆分后 0/60 失败。

这三条一起排除了「计时器测的是别的东西」和「读数是个与负载无关的常数」两种撒谎方式。

## 5. 两个万人特有风险(DoD 5)

### 5.1 `hashtext` 碰撞

**实测碰撞率**:2000 组 × 每组 10000 个 cuid 形状 id,其中 **18 组**出现碰撞 ——
**0.90%**,理论值 1 − e^(−λ)(λ = C(10000,2)/2³² = 0.0116)= **1.16%**。
观测 18 次 vs 期望 23.2 次,在 Poisson 噪声内(σ ≈ 4.8),实测与理论一致。
本次探针实际使用的那 10000 个 id 碰撞对数 = **0**。

> 组数取 2000 而不是 300:碰撞率只有 ~1.2%,300 组期望才 3.5 次,观测到 1 次和 5 次
> 都在噪声里 —— 那种样本量下说「实测≈理论」是自欺。(300 组的首次试跑确实只中 1 次,
> 换算成 0.33%,与理论差 3.5 倍,纯属样本不足。)

**后果:两者都是 —— 主要是「不同队员被迫串行」,但存在一条真实的死锁边,不是纯性能问题。**

- **串行(必然)**:两个不同 memberId 映射到同一个 advisory 键 ⇒ 本不相干的两个队员
  被迫互斥。这是**过度加锁**,不会漏锁,所以**不产生数据正确性问题**(锁域是真实需求的超集)。
- **死锁(可能,机制已实测触发)**:`lockMembersForWrite` 用 `ORDER BY member_id` 固定取锁顺序,
  但真正的锁键是 `hashtext(member_id)`。**排序键与锁键不是同一个东西**。一旦 a ≠ b 而
  key(a) == key(b),再有第三个 c 满足 a < c < b,则
  - 批次甲 {a, c} 的取锁序 = key(a), key(c)
  - 批次乙 {c, b} 的取锁序 = key(c), key(b) == key(a)

  **两者反序**,构成死锁边。`member-advisory-lock.util.ts` 注释里「两层同向 ⇒ 不同批次之间
  不会反向取锁」的论证,在碰撞出现时不成立。

  探针用一对**真实**碰撞 id 验证了这条:
  `c841bb8f66366ad0ab58eda83` 与 `c86b3e165b8154656a71ffe8a`,`hashtext` 同为 `-1901144566`。
  - **机制实验(显式交错两个事务)**:✅ **实测触发 40P01**
    `ERROR: deadlock detected / DETAIL: Process ... waits for ExclusiveLock on advisory lock ...`
  - **自然并发实验(两侧各自一条语句对撞)**:60 次尝试观测到 40P01 **0 次**。

  即:**是结构隐患,不是本机能稳定复现的活 bug** —— 单条语句内两把锁前后相隔微秒级,
  自然并发撞进这个窗口的概率极低。后果是 PostgreSQL 检测到并中止其中一个事务(40P01),
  **不是静默的数据错误**;但 40P01 目前不在 `withBoundedMemberLockWait` 的翻译范围内
  (那里只翻 55P03 → 40901),会以未映射错误冒出去。

  发生条件叠加:该场有碰撞对(0.90%)× 碰撞对之间恰好夹着第三个同批成员 × 两个批次并发。
  万人场景下每场 0.90% 已经不是可以忽略的量级,但要凑齐全部条件仍属小概率。

### 5.2 `Prisma.join` 构建耗时与 bind 参数上限

**构建与执行分开计**(DoD 明确要求):

| 规模 | `Prisma.join` 构建 P50 | 该语句 bind 参数数 |
| --- | --- | --- |
| 30 | 0.0 ms | 30 |
| 500 | 0.1 ms | 500 |
| 2000 | 0.3 ms | 2000 |
| 5000 | 1.1 ms | 5000 |
| **10000** | **1.8 ms** | 10000 |

10000 档 ①段总耗时 P50 = 13.8 ms,其中**构建 1.8 ms(13%)**,
**执行(一次往返 + 取 10000 把锁)≈ 12.0 ms(87%)**。构建 10000 个片段不是瓶颈。

**bind 参数上限:撞到了 —— 但不是 65535 那一条。**

DoD 让我确认「没有撞 PostgreSQL 65535 bind 参数上限」。实测二分的结果是:
**先撞上的是 Prisma 查询引擎自己的 32767**(有符号 i16),只有协议值的一半。

```
最大可用 32767 个;32768 个失败:
Assertion violation on the database:
`too many bind variables in prepared statement, expected maximum of 32767, received 32768`
```

按**实测值**推导本事务内四条语句的人数上限:

| 语句 | 每人参数 | N=10000 时 | 撞 32767 时的 N | 余量 |
| --- | --- | --- | --- | --- |
| ① advisory 取锁 VALUES | 1 | 10000 | 32767 | 228% |
| ② day-state `FOR UPDATE` join | 2 | 20000 | 16383 | 64% |
| **③ day-state 批量 UPDATE** | **3** | **30000** | **10922** | **9%** |
| ④ result revision UPDATE | 1 | 10000 | 32767 | 228% |

**③ 是硬天花板,且这已经是最省的写法。** 本探针每人只回写 **1 个**业务值就用掉 3 个参数
(member_id + ledger_date + 1 个值),余量只剩 9%。合同 §5.13 第 7 步要求 day-state
「版本递增**和合计更新**」,真实实现至少要回写 recognized / credited / cappedOut:

- 每人 4 参数 ⇒ 上限 **8191 人**
- 每人 5 参数 ⇒ 上限 **6553 人**

**两者都低于 10000。** 也就是说:按合同字面「一条批量 UPDATE 把万人 day-state 一次写完」
的实现方式,**在写第二个业务字段时就会撞墙**,而且是确定性失败,不是概率问题。
这不是性能余量问题,是 schema / 实现方式的硬约束。

## 6. 探针额外发现:共享锁表天花板

不在 DoD 五条内,但属于万人特有风险,如实记录。advisory 锁占用 PostgreSQL 的**共享**锁表:

- **公式保底** = `max_locks_per_transaction × (max_connections + max_prepared_transactions)`
  = 64 × 200 = **12800**。这是文档保证的容量。
- **单事务实测上限**(空载服务器,二分粒度 1000):**22000 把通过,23000 把失败**
  (`ERROR: out of shared memory`)。高于公式保底,是因为锁哈希表可以机会性地占用
  共享内存里剩下的空间 —— **这部分不是保证,会随其他 backend 的用量缩水**。
- 10000 人一次生效占公式保底额度的 **78%**。

推论(手工验证过 2 并发确实成功):

| 并发万人生效数 | 需要的锁槽 | vs 公式保底 12800 | vs 实测上限 ~22000 |
| --- | --- | --- | --- |
| 1 | 10000 | 78%,在保底内 | 安全 |
| 2 | 20000 | **156%,超出保底** | 空载实测可过,无保证 |
| 3 | 30000 | 234% | **必然失败** |

`out of shared memory` 是硬 ERROR,不是锁等待:它不会走 `lock_timeout` → 55P03 → 40901
那条可重试路径,而是直接中止事务。**同时有两场万人活动统一生效**在当前 PG 配置下已经
越过文档保证线。

## 7. 结论与可选路径(不实施,交维护者拍板)

**时间预算这一条:通过。** 合同 §5.13 / §10.6 关心的「10000 人能否在现有 7 秒预算内完成」,
答案是能,且余量很大(P99 286.8 ms,24× 余量)。**不需要**升级锁框架或重新拍板生效粒度
来解决时间问题,也**不需要**调大任何 timeout —— 本报告没有改动任何预算常量。

但有三条必须在第 1 批 schema lane 开工前拍板,**本 goal 一条都没有实施**:

1. **【硬约束】day-state 批量写的 bind 参数上限**(§5.2)。按合同字面写法,回写 2 个以上
   业务字段就会在 8191 人处确定性失败。可选路径:
   (a) 把批量 UPDATE 改成 `UPDATE ... FROM (SELECT unnest($1::text[], $2::date[], ...))`,
       数组参数与人数无关,一次搞定;
   (b) 分块写(每块 ≤ 3000 人)在**同一事务**内循环 —— 语句数变成 O(N/3000),
       与本仓「SQL 次数固定」的批量化判据冲突,需要单独拍板;
   (c) 用 `COPY` 到临时表再 join 更新。
   三条都属于实现方式,不改锁语义。
2. **【配置】共享锁表容量**(§6)。若允许两场万人活动并发生效,需要提高
   `max_locks_per_transaction`(生产库配置变更,需重启)。属于运维决策,不在本仓代码内。
3. **【结构隐患】`hashtext` 碰撞造成的取锁反序**(§5.1)。修法是让取锁顺序按**锁键**
   而不是按 member_id 排序(即 `ORDER BY hashtext(member_id)`),或在 40P01 上补一层
   有界重试。合同 §16 明写:若探针证明现有 API 不足,**另立 goal 改,不在活动 PR 顺手改**——
   本报告照此办理,只报不改。

## 8. 本探针未覆盖的(诚实边界)

- **零锁竞争**。全部读数在单客户端、无人争锁的条件下取得。7 秒预算 = 4 秒锁等待 + 3 秒业务工作;
  本报告测的是**业务工作那 3 秒**的占用(P99 286.8 ms,约 10%)。真实并发下还要加排队时间。
- **`current-state` §4 已登记的 P2 债未被触碰**:`lock_timeout` 是 per-acquisition,
  多次顺序锁等待会相加撞穿 7 秒总预算。本 goal 只测量、不修它,也未构造该场景。
- **单日账期**。fixture 是 10000 人 × **1** 个 ledger_date。跨天活动的 day-state 行数随天数
  线性增长,②③ 两段与 bind 参数上限都会按同一倍数恶化(3 天活动 ⇒ 3 万行 ⇒ §5.2 的上限
  再除以 3)。
- **合成 id、合成表**。用的是 cuid 形状的合成 memberId 与探针自建的表,不是真实
