## A-1 · 申请人本人的证书编号保持掩码

- **涉及**:§15.4 敏感分级
- **原文**:申请人可以看自己提交的完整证书编号。
- **改为**:申请人侧**只返掩码**(`certNumberMasked`),不提供完整编号。
- **理由**:编号是申请人自己填进去的,返还给他**零信息增量**,却多开一个 L2 数据的暴露面 —— 公开端点的每一个明文字段都是一条要长期守住的边界。
- **触发来源**:维护者 2026-07-30 拍板(跨模型评审 findings 修复批次立项时)。
- **实现影响**:**无**。当前实现本来就是掩码 —— 本条修正消除的是「文档说完整、接口给掩码」这个矛盾,不是改代码。

## A-2 · Policy 状态接口只允许 ACTIVE

- **涉及**:§13.2 认定规则管理面
- **原文**:「激活 DTO 只允许 ACTIVE」+「当前 ACTIVE Policy 由激活动作自动 RETIRE,不让客户端分两步操作」。
- **实现曾偏离**:DTO 多接受了一个 `RETIRED`(「手动退役当前 ACTIVE 版而不立新版」),且代码注释自承偏离。
- **改为**:**恢复冻结契约,只接受 `ACTIVE`。**
- **理由**:手动退役会让该 Standard 进入「有标准、无生效规则」状态,此后既不能建证也不能过审(`18035` / `28062`)。那是一个**真实的运营动作**(「暂停认定这类证书」),需要它自己的权限判定、审计语义和前端提示 —— 不该由一次「顺手多接一个枚举值」的 DTO 改动带进来。真有这个诉求就单独立项。
- **触发来源**:维护者 2026-07-30 拍板 + 跨模型评审 V6。
- **实现影响**:契约收紧。发 `status: RETIRED` 从 200 变 `40000`。

## A-3 · DRAFT 标准可改身份字段(`code` 除外)

- **涉及**:§7.1 标准生命周期 / D-CERT-004(code 不可复用)
- **原文**:身份字段(`kind` / `categoryCode` / `levelCode` / `parentId` / `isInternal`)创建后一律不可改;DRAFT 期要改就**删掉重建**。
- **改为**:DRAFT 且**从未启用过**(`activatedAt IS NULL`)时,上述五个字段**可改**;`code` 仍然一个字都不能改。
- **理由**:「删掉重建」这条路在本模型里**走不通**。`code` 是全量 `@unique` 且**含软删行** —— D-CERT-004「code 不可复用」正是靠这一点实现的。于是软删一个填错的 DRAFT 标准之后,它的 code 被永久占用,「重建」只能换一个 code。首批初始化时打错一个字,那个 code 就永远用不了了,而 code 是要被岗位要求、活动门槛、外部系统长期引用的稳定标识。
- **为什么判据是 `activatedAt` 而不是 `status !== DRAFT`**:状态机允许 `ACTIVE → INACTIVE → ACTIVE`,而 `activatedAt` 记的是**首次**启用时刻且永不被覆盖 —— 它才是「这个标准有没有对外生效过」的那个事实。只看 status 会把一个 INACTIVE 标准误判成可改身份,而它可能已经被一批历史证书引用着。
- **触发来源**:跨模型评审 R2。

## A-4 · 只有 DRAFT 标准可软删

- **涉及**:§7.1 / §18(`CERTIFICATE_STANDARD_IN_USE`)
- **原文**:未明确限定可删状态,只规定「被引用时禁删」。
- **改为**:**只有 DRAFT 且从未启用过的标准可软删**;ACTIVE / INACTIVE 一律拒(`18032`)。引用计数守卫保留,作为第二道。
- **理由**:引用计数拦得住「有引用的」,但零引用的 ACTIVE 标准照样能删 —— 而删掉的后果是「这个 code 被永久占用(含软删行的 unique)且再也建不出来」。停用一个标准的正确动作是 `INACTIVE`(不再新发),不是软删。
- **触发来源**:跨模型评审 R3。
- **连带**:「被子节点引用 → 18032」这个组合经 API 已不可达(挂子节点要求父为 ACTIVE,而 ACTIVE 不可删)。守卫保留(seed / 运维直写仍可能造出该状态),对应 e2e 改为直插构造。

## A-5 · Standard options 两档都只返 ACTIVE

- **涉及**:§13.1 标准选择器
- **原文**:`recognizedOnly=true` 要求「ACTIVE 且有 ACTIVE Policy」;不传时未明确排除 INACTIVE。
- **改为**:**两档都只返 ACTIVE 标准**。两档的区别收窄为「要不要**同时**有 ACTIVE Policy」。
- **理由**:INACTIVE 标准在 Resolver 那里是硬拒(`assertStandardIsActive`)。缺省档返回它们,等于下拉里明明列着、甚至因为它还挂着一条 ACTIVE Policy 而显示 `currentlyRecognized: true`,选中提交却被拒。「能选但选了就报错」是最难排查的一类前端问题:报错信息指向标准状态,而用户看到的界面上根本没有状态这一列。
- **触发来源**:跨模型评审 R5。
- **保留不变**:§11.2「已收录、待认定」(ACTIVE 标准 + 无 ACTIVE Policy)仍在缺省档返回,`currentlyRecognized: false` —— 那是一个正常状态,不是被排除的对象。

## A-6 · 发号收尾终结全部非 PROMOTED 申报

- **涉及**:§8.5 发号搬运
- **原文**:第 9 步只规定 `APPROVED` Claim 转 `PROMOTED`,未提及其余状态。
- **改为**:发号收尾把该报名下**全部非 `PROMOTED`** 的未软删申报级联为 `WITHDRAWN`,与「整份报名撤销」那条路径逐字同口径。
- **理由**:按原文实现的结果是,一份已 `promoted`(终态)的报名下可以永久残留 `SUBMITTED` / `NEEDS_INFO` / `REJECTED` 的申报 —— 它们永远不会再变成证书,却仍然可被审核、仍可签发证据 URL。这破坏了「终态报名下不存在非终态 Claim」这条不变量,而且**不需要并发就能复现**。
- **触发来源**:跨模型评审 findings 修复批次 F1 实施时发现(原报告未列此条)。

## A-7 · 核验已过期证书直接落 expired

- **涉及**:§9.3 核验动作
- **原文**:核验通过 → `verified`;`expired` 由每日到期扫描 cron 推动。
- **改为**:核验时若**最后有效日已早于今天**(北京日历日),直接落 `expired`。边界:最后有效日**当天**仍是 `verified`。
- **理由**:到期扫描 cron 只处理**已经是 `verified`** 的行,而核验动作正是产出 `verified` 行的地方 —— 按原文实现会亲手造出一张「最后有效日已过却是 verified」的证书,它会一直被资质判定当作有效,直到次日 09:00 cron 跑过。发号路径(§8.5 第 8 步)早就按同一规则分流了,管理端核验没跟上。
- **触发来源**:跨模型评审 V7。

## A-8 · 撤回审核不复用审核字段

- **涉及**:§8.2 末段(撤回审核)
- **原文**:「必须清空 resolved Standard / Policy / issuer 与审核字段,并写高价值审计。」
- **实现曾偏离**:清空了 Standard / Policy / issuer,但把**撤回人**写进 `reviewedByUserId` / `reviewedAt`、把**撤回理由**写进 `reviewNote`。
- **改为**:三列一并**清空**。撤回人由审计的 `actorUserId` 承载,并额外记 `revokedReviewerUserId`(被撤销的那次审核是谁做的);撤回理由按 §17「Claim 审计不含备注全文」只记 `noteProvided` 布尔。
- **理由**:那三列的语义是「谁、什么时候、以什么理由**通过**了这条申报」。撤回后复用它们,会让一条 `SUBMITTED` 的申报上挂着「审核人:张三」,而申请人侧看到的 `reviewNote` 会把撤回理由读成驳回说明 —— 两处都是误读,且从数据上无法区分。
- **触发来源**:跨模型评审 R9。
- **代价**(明确记录):撤回理由的**全文不再持久化**。§17 禁止备注全文进 Claim 审计,而 Claim 行上又不该有它。若将来需要留存撤回理由,应新增专门的字段或审计事件,而不是回头复用审核三列。
