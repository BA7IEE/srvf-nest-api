# 开发与交付

1. 核对实际代码和相关测试。新工作树安装锁定依赖并生成 Prisma client。任务分工与交接见下节。
2. 在已授权范围内完成实现。只有新增业务决策、不可逆操作或扩大范围需要再次询问维护者。
3. 运行相关检查，审阅 diff。日常用 `pnpm agent:check:quick`，提交前冷 lint；
   API 变化运行 contract、OpenAPI/client freshness 与定向 E2E。全量 E2E 由 CI 运行。
4. PR 说明问题、改后行为、验证及剩余限制。业务变更写 `changelog.d/` fragment；
   不再要求同步 CODEMAP、计数、Goal、NEXT_TASKS 或冻结稿台账。
5. CI 的四个 required check 名保留：
   `Lint / Typecheck / E2E`、`Docker image build`、`Diff guards`、`Red-zone (trusted)`。
   最小红区由 base 上的裁判检查，维护者人工批准。不要代点审批或把待审批写成已通过。
   Draft 转 Ready 不重复审批同一提交；修改 PR 基底时先把目标分支同步进 head，
   触发新扫描与验证，不复用旧基底的绿灯。模块 `CLAUDE.md` 本身不触发运行时代码审批。

## 任务协作与交接

- 每项任务约定范围、完成条件和一位负责人。负责人跟到验证、集成和实际收尾。后续消息默认补充原目标，明确改目标时再调整范围。
- 开新会话前，先查接口、代码、数据和环境依赖，核对在跑任务、进程、机器负载与服务限额。独立任务有并行收益时可分别由多个 Codex 主会话承担，各自按需分工给子代理，并将主、子会话合计计入并发。改代码用独立工作树，共享资源指定一位写入负责人。
- 互斥只覆盖登记的任务和共享资源。先保留在跑任务并核对锁的持有者，避免重复启动、同目录写入、同环境互改或覆盖他人工作。现阶段优先完成生产只读核查。Issue/PR 清单和最小 API、Worker 方案经核实与现场核查独立时，可并行处理。
- 连续工作优先沿用原会话，只传必要背景、有效约束和证据。大日志保留可追溯位置，向上报告结论、位置和不确定项。目标切换、信息混杂过时或多次尝试无进展时，可压缩上下文或交接新会话。交接写清目标、版本、改动、有效决定与依据、未验证项和下一步，接手人先核实当前事实和在跑任务。
- 实现者完成必要自测后，由未参与实现的人按需求、约束和精确版本检查实际差异、关键行为与证据，独立给出结论。合并前保留受审提交和审查来源，作者换名自评仍算自测。未参与实现的子代理也可独审，按可核对的记录确认身份与结果，无需固定会话或另开主会话。连续修复无进展时，重查假设与复现条件，必要时换人复核。补测受影响范围，保留断言并追查失败。
- 集成负责人固定最终配对版本，补验受影响流程及任务要求的真实服务器行为。分别记录代码完成、合并、部署、实际验收的状态。按各 Issue/PR 自身的完成条件和证据收尾，延期写明负责人、原因及恢复条件。

## 发布

仅在维护者授权后执行。先 `pnpm release:prepare <版本号>` 生成文件，审阅、验证并走 PR；
合并状态确认后再 `pnpm release:finish <版本号>` 打 tag、创建 GitHub Release。
发版不等于生产部署，现场切换另按 `docs/ops/` 对应 SOP。
清理工作树前确认 GitHub 已合并及本地没有未保存工作；不强删、不批量清理无关工作树。
