# 切换前检查 —— 维护者签字登记(cutover sign-off)

> 合同 §16.1 的十条切换前检查里,**B 类**(机器可查·人判定)与 **C 类**(只能人判)的结论
> 按设计就该由人来下。本文件是那个「下结论」的**唯一落点**,`pnpm cutover:check` 每次运行都读它。
>
> 判据侧:[`scripts/cutover-check.ts`](../../scripts/cutover-check.ts)。

## 0. 为什么要有这份文件 —— 在它之前,签字这件事**物理上不存在**

`cutover-check.ts` 的 `eviSub()` 原本把 `verdict` 硬编码成 `'pending'`:

```ts
function eviSub(id, kind, title, evidence): SubCheck {
  return { id, kind, title, verdict: 'pending', evidence };   // ← 写死
}
```

⇒ **9 条「⏸ 待维护者确认」签一百次也不会变。** 这道闸被设计成了「永远开不了」——
而维护者 2026-08-26 拍板「直接用新的上线」(不按运维手册的「首次上线填 false」),
**这道闸正是通往那个决定的唯一路径**,它开不了,那个决定就落不了地。

## 1. 🔴 签了 ≠ 过 —— 签字本身也要被验

一个「签了就放行」的机制**等于把闸拆了**。本仓 2026-08-26 一天内已两次逮到
「名单 / 腐烂检测是摆设」(#1184 豁免名单指着已删文件;#1195 把腐烂检测改成恒返回空照样全绿)。
所以这里的四种结局是**不对称**的:

| 情形 | 结论 | 影响退出码 |
|---|---|---|
| 签了,且签字里记的读数与机器现读**逐字相等** | ☑ 已签字确认 | 否 |
| 签了,但与机器现读**矛盾** | ❌ 签字与机器读数矛盾 | **是** |
| 没签 | ⏸ 待维护者确认(现状) | 否 |
| 签了一条闸里**不存在**、或**不接受签字**(A 类)的编号 | ❌ | **是** |
| 登记表不存在 / 声明条数与解析条数不符 / 块头被改坏 | ❌ | **是** |

⚠️ **A 类子判据不接受签字。** 那是机器判出来的结论,人签不动它 ——
否则「用一张签字把 9a 的 todo 抹平」就成立了。签 A 类编号当场红。

⚠️ **签过字的 B/C 渲染成 `☑` 而不是 `✅`。** 机器判的绿勾与人签的确认视觉上必须分得开:
「这个结论是谁下的」是复核时第一个要问的问题。

## 2. 怎么签(六项,缺一即红)

一条签字 = 一个 `### <编号> — <标题>` 块 + 六个字段行。**字段行的形状是判据的一部分**,
照抄下面的模板即可;写坏了不会静默丢失,会当场红(判据失去输入 ≠ 通过)。

```md
### 5b — 五端支持同一 contract version(登记表读数)

- **结论**:认可
- **理由**:<为什么这么判 —— 一行,长短不限>
- **签字人**:维护者
- **日期**:2026-08-26
- **依据**:<拍板出处:goal / PR 链接 / 会议纪要>
- **对拍**:有 —— `<读数键>` = `<签字当时的读数>`
```

- **结论**只认闭集 **`认可` / `不认可`** —— 「大概可以」「基本认可」这类模糊结论不是结论,当场红。
- **日期**必须是合法日历日(`2026-02-30` 形状对但不存在,当场红)。
- **对拍**写 `无` 时**必须写明为什么无**(`无 —— <理由>`),不许静默地把对拍取消掉。

改动本表后,**同一个 PR 里**把下面这行的数字改对(少一条签字**不产生任何坏链接**,只有这行看得见):

**签字条数(机器核对):4 条**

## 3. 可对拍的读数(闭集)

签字里写的每个读数键都必须在这张表里。**键打错一个字母就红** ——
若判据只是「查得到就比、查不到就跳过」,那条对拍会静默失效,这正是本仓栽过两次的形状。

| 键 | 读的是什么 | 它一变说明什么 |
|---|---|---|
| `migration-total` | `prisma/migrations/` 下的目录数 | 新落了一条 migration ⇒ ③-b「经审查」的覆盖面变了,得重签 |
| `backend-contract-version` | `package.json#version` | 后端发过版 ⇒ ⑤-b「五端同一版本」的前提变了,得重签 |
| `contract-registry-rows` | 契约版本登记表解析出的行数 | 有人删了一行 ⇒ 缺口被洗掉 |
| `contract-version-mismatch-count` | 登记表里与后端版本**不一致**的端数 | 0 → N ⇒ 五端不再对齐,而签字还在 |
| `review-report-sha256-12` | ①-b 那份复核报告的内容摘要 | 报告被改 / 被删 ⇒ 那次签字所依据的东西已不在 |

当前读数由 `pnpm cutover:check` 在「签字登记」一节逐行打印 —— **别在本文件里抄读数**,
抄一份就是第二处声明,它会随发版静默过期。

## 4. 签字登记

### 1b — 「通过不同模型复核」

- **结论**:认可
- **理由**:仓内有 `SRVF_活动业务文档_系统性对抗性复核报告_v1.0.md`(复核日期 2026-08-02)。⚠️ **该报告早于修订件 `AMENDMENTS-v1.1.1`** —— 维护者知晓此局限并选择认可
- **签字人**:维护者
- **日期**:2026-08-26
- **依据**:维护者 2026-08-26 拍板「直接用新的上线」;局限已在理由里写明,是这次签字的**已知折扣**
- **对拍**:有 —— `review-report-sha256-12` = `f22d34e0d535`

> ⚠️ 这条的**结论**只能由人下(机器无从判断「不同模型」与「通过」)。
> 对拍锚的是**那份复核报告的身份**:报告被改动或删除 ⇒ 这次签字所依据的东西已不在 ⇒ 必须重签。
> 对拍**不代替**结论 —— 它只保证「你签字时看的那份东西,现在还是那一份」。

### 2a — 本 worktree 的红区授权令牌(只增不减、无过期、per-worktree)

- **结论**:认可
- **理由**:当前令牌仅 1 条(`scripts/check-activity-workflow-gate.ts`),理由字段完整可追溯
- **签字人**:维护者
- **日期**:2026-08-26
- **依据**:维护者 2026-08-26 拍板「直接用新的上线」
- **对拍**:无 —— 令牌是 **per-worktree** 的(落在 `$(git rev-parse --git-path srvf-redzone-grant.json)`,每棵 worktree 各有各的),**不是仓库事实**;拿它对拍会在别的 worktree 里恒红,那是假红不是执法

> 🔴 **本条有一处已知的读数出入,留在台账上不掩盖(2026-08-26 lane 实测)**:
> 主仓 `/Users/dengwang/Documents/coding/srvf-nest-api` 当日 `pnpm harness:grant --list` 读到的是
> **2 条**令牌(`scripts/check-activity-workflow-gate.ts` 2026-08-25 02:29 + `AGENTS.md` 2026-08-25 15:52),
> 而交付本刀的 worktree `cc-signoff` 读到的是 **0 条**。
> 签字理由里的「仅 1 条」是拍板当时的读数,**与今天任一处读数都不相等** ——
> 这正是「per-worktree 的量不能拿来对拍」的实例。
> ⇒ 2a 这条的**准确结论需要维护者复核一次**:若他要的是「开闸前令牌必须清空」,
> 那就该先 `pnpm harness:grant --clear` 再重签;若他接受留着令牌,理由行应订正成当时真实的条数。
> **本刀不替他改结论**,只把出入摆在这里。

### 3b — 「新 schema migrations 经审查」

- **结论**:认可
- **理由**:99 条 migration;本批新增的每一条都经 CI 冷跑全量重放通过
- **签字人**:维护者
- **日期**:2026-08-26
- **依据**:维护者 2026-08-26 拍板「直接用新的上线」;逐条留痕在各 D 档 PR 的评审记录里
- **对拍**:有 —— `migration-total` = `99`

> ⭐ 这条对拍的价值在于它**会过期**:再落一条 migration ⇒ 读数 100 ≠ 签字里的 99 ⇒ 当场红,
> 维护者必须为**新增的那条**重新签字。「经审查」的覆盖面因此不会随时间静默扩大。

### 5b — 五端支持同一 contract version(登记表读数)

- **结论**:认可
- **理由**:后端 0.69.0;登记表合同点名 5 端、解析到 5 行,机器已对齐
- **签字人**:维护者
- **日期**:2026-08-26
- **依据**:维护者 2026-08-26 拍板「直接用新的上线」;登记表见 [`docs/handoff/contract-version-registry.md`](../handoff/contract-version-registry.md)
- **对拍**:有 —— `backend-contract-version` = `0.69.0`;`contract-registry-rows` = `5`;`contract-version-mismatch-count` = `0`

> 🔴 三个读数各堵一条腐烂路径:
> **版本号**变了(发版)⇒ 「五端同一版本」的前提整个变了,得重签;
> **行数**从 5 变 4 ⇒ 有人把填不出的那行删掉、把缺口洗成「零不一致」;
> **不一致端数**从 0 变 1 ⇒ 某端报的版本与后端对不上,而签字还在 —— 这一条正是本机制的靶心。
>
> ⚠️ 登记表当前 5 行里有 1 行「同后端」(worker,同仓同构建)、4 行「未回执」。
> 「未回执」**不算不一致**(无从核对),所以 `contract-version-mismatch-count = 0` 是真的;
> 维护者签的是「机器已对齐」,**不是**「四端已回执」—— 后者的缺口仍在那张表上,没有被这次签字抹掉。

## 5. 永久豁免登记(验收编号「已判定不做」)

> 合同的验收编号只有两种结局是不够的:**有去向**(真用例)与**被卡住**(`it.todo`)。
> 「维护者已拍板永远不做」这一类此前无处安放 —— 只能挂成 `it.todo`,让 ⑨-a 的「零 todo」永远红。
>
> 🔴 **不许直接删掉那几条编号**:删了就没人知道合同里还有这几项。
> 🔴 **也不许放宽 ⑨-a 的「零 todo」口径** —— 那是判据,不是旋钮。
> ⇒ 落点是**第三种渲染**:真用例,断言「该豁免确实被登记了、写明理由与拍板人」。
> 判据侧见 `src/modules/activities/activity-business-overhaul-acceptance.spec.ts` 的
> `PERMANENT_WAIVER_ACCEPTANCE_DESTINATIONS`。

改动本节后,**同一个 PR 里**把下面这行的数字改对(判据逐字比对它与登记表条数):

**永久豁免登记(机器核对):4 条**

### 共同根因(四条同一条天花板)

统一生效走 `runMemberLinearizedTransaction`,被 `LEDGER_COMMIT_LOCK_SLOT_COUNT = 10` ×
`LEDGER_COMMIT_MEMBERS_PER_SLOT = 1000` 闸住 ⇒ **一场万人恰好用尽全部 10 个槽 = 10000 把队员 advisory 锁**;
而 PG 共享锁表公式保底 **12800 是整个实例共享**的(不是每库一份),e2e 各 jest worker 派生独立库
却共用同一个 PostgreSQL 实例 ⇒ 一条万人用例占掉全实例 **78%** 的锁表条目,
**两场并发即 `out of shared memory`**。那是**硬 ERROR**,而且会撒到**别的 spec** 上
—— 不是「跑得慢」,是造 flake 机器。

⚠️ 这四条**不等于合同这四句作废**。它们仍在合同里、仍在追踪矩阵里,只是**规模门**这一格
由 ⑨-b「规模测试通过」承载(那是独立一格,仍是 ⏸ 待维护者确认),不再由 ⑨-a 的验收套件承载。

## 6. 这份文件**不**做什么

- **不替代 ⑤-b 的契约版本登记表**([`docs/handoff/contract-version-registry.md`](../handoff/contract-version-registry.md))。
  那张表收的是**四端的证词**;本表收的是**维护者对那些证词的判断**。两件事,两张表。
- **不让 A 类子判据变绿。** A 类由机器判,签字对它无效(签了当场红)。
- **不记录读数。** 读数由 `pnpm cutover:check` 现算现打印;本表只记「签字当时看到的值」,
  好让机器发现「今天的值已经不是那个值了」。
