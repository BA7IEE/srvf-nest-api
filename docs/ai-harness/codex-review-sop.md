# Codex 交叉评审 SOP(Harness 2.0)

> 依据:公理 A5 —— 同一模型自写自查,错误相关会一起漏;写与查必须跨模型。协议条文在 [`process.md §8.3`](../process.md);本页是操作 SOP。仓库 `AGENTS.md` 恰是 Codex 原生自动读取的规则入口,无需额外配置。

## 1. 何时评审

- **必须**:红区 / D 档 PR(schema · auth · 权限 · harness 文档重写 · workflows)。
- **必须**:**每个大批次收尾时对整批做一轮**(见 §1.5)。
- **尽量**:B/C 档实质 PR 合并前过一遍。
- **可免**:A 档 docs-only。

## 1.5 批次级评审(2026-07-29 起,以实证替代原计划的「埋雷考核」)

单 PR 评审看不见**跨 PR 的结构性问题**。Harness 3.0 十六个 PR 逐个都合规,
合起来却漏掉了信任根 —— 那不是任何单个 PR 的缺陷,是整批的缺陷。

**触发**:一个多 PR 批次(蓝图阶段 / 大重构 / 全仓 review 的修复批)合并完毕后,
发版前跑一轮,对象是**整批 diff**而非单个 PR。投放模板见 §2,把范围换成
`<批次起点>^..<当前 main>` 并列出该批全部 PR 号。

**为什么这条取代了「埋雷考核」**(原 P7 计划:往仓库植入已知缺陷,看守护抓不抓得到):

- **实证收益悬殊**。2026-07-29 首次批次级评审:两个外部模型给出 4 个 BLOCKER,
  **逐条实测全部属实**,其中一条(测试库安全闸只查 `app_test` 子串 + `.env.test`
  不受保护)可对远程数据库执行全表 TRUNCATE。而同一批代码的**自查**只找出
  4 条较浅的问题 —— 数字对不对、断言能否被绕过 —— **一个 BLOCKER 都没找到**。
- **埋雷考核有同源盲区**。雷由谁埋?若由写 harness 的同一模型埋,它埋的正是
  它想得到的那类缺陷 —— 而真正的漏洞恰恰在它想不到的地方(信任根、控制面、
  生产入口)。这与「自写自查一起漏」是同一个失效模式,只是换了层皮。
- **成本更低**。埋雷要造缺陷、跑 CI、清理现场,还污染 git 历史;批次评审只花
  维护者约 1 分钟投放。

**findings 处置**:沿 §3。额外一条 —— **报告里的机制描述必须自己复现后再采信**。
首轮实测中,报告归因的机制有两处与实际不符(其一把 flake 归因为「Prisma 默认
5s 事务预算」,而该处事务明确给了 20s)。**结论属实不等于机制正确**,照着错的
机制去修会修错地方。

## 2. 怎么投放(维护者动作,约 1 分钟)

把 PR 链接交给 Codex(CLI / IDE / 云端任一形态),附模板:

> 请评审 <PR 链接>。要求:
> ① 对照 PR body「写集声明」核对 diff 是否越集;
> ② 找正确性 / 安全 / 并发问题,给"文件:行号"证据;
> ③ 对照 AGENTS.md §1 铁律速查与 §2 决策锁,标注任何违反;
> ④ 结论分级 BLOCKER / SHOULD-FIX / NIT;没有问题就明说,不要凑数。
> findings 以评论发在 PR 上(或输出给我粘贴到 PR)。

## 3. findings 处置(总控)

- 落点统一 = **PR 评论**;总控逐条消化:接受 → 修并回帖;不接受 → 评论给理由。
- **分歧不内部调和**:两模型结论相反 → 原样升级进人话简报由维护者裁(分歧点 = 维护者注意力的优先级信号)。
- findings 与处置留在 PR 记录,不进仓库正文。

## 4. 边界

- Codex 评审是只读的,不授予直接改仓库。
- Codex 承接执行 lane 时(限 A/B 档,goal 立项),对称规则生效:Claude 评审其 PR。
- 本页更新走 A 档 PR;与 process §8 冲突时本页让步。
