## 1. 方法与覆盖率

### 1.1 归因单位

**增长 commit 的净新增行**,不是文件当前构成 —— 问的是「长出来的是什么」,不是「现在是什么」。
逐条 (commit, file) 记录:取 `git diff -U0` 的新增行与删除行,各自在**对应版本**的文件上判层,
`净增(某层) = 新增(该层) − 删除(该层)`。故某层出现负值 = 该层在增长 commit 里净减少(合法读数)。

### 1.2 窗口与覆盖率

窗口 = `main` 全部 **1024** 个 first-parent 提交(本仓 squash merge,一提交 ≈ 一 PR)。
发现面 = 6-A 基线的 31 个文件。

| 口径 | 增长 commit | (commit,file) 记录 | 已归因 | **覆盖率** | 新增 NCLOC | 删除 | 净增 |
|---|---|---|---|---|---|---|---|
| 宽(任何增长) | 177 | 270 | 270 | **100%** | 39841 | 3396 | 36445 |
| 严(增长时已超阈值) | 91 | 135 | 135 | **100%** | 10250 | 2399 | 7851 |

**不做抽样,全量归因** —— 故无「抽样覆盖该域增长量 X%」的折扣。
下文表格**以严口径为主**:沿立闸报告 §3 自己的判断「文件初建或尚小时的增长今天不会再发生一次,
严口径更贴近未来实况」。宽口径同时给出。

### 1.3 分类轴(沿用既有 D-7 六类,不另造体系)

| 归属 | 类 | 判据要点 |
|---|---|---|
| **可搬** | Presenter / QueryService / Policy / StateMachine / AuditRecorder / Effect | `architecture-boundary.md` §3 六类 |
| **可搬(相邻既定范式)** | Calculator | §5 明列 `contribution-calculator.ts` 为 accepted adjacent pattern,单列不并入六类 |
| **不可搬** | 事务编排 | 事务边界持有者(`$transaction(async (tx)=>…)` **及具名事务包装器**,见 §2.4 缺陷 3)、其内的写协调与调用编排、聚合根装载(§4 逐条明列) |
| **其他(具名,不作垃圾桶)** | 控制流与过程代码 / 方法签名与结构 / 类型与常量声明 / import 与 DI 接线 | 四类各自具名,不合并 |

两条关键口径,都直接来自 §3/§4 的原文而非我的发挥:

- **audit / policy / state / presenter / effect 即使写在事务回调体内也计「可搬」** ——
  §3.5 明写 AuditRecorder「calls to `AuditLogsService.log(...)` **with the transaction passed in**」,
  即收 tx 是设计,不是留在 service 的理由;Policy / StateMachine 是纯判定,同理。
- **事务回调体内的读计「不可搬」** —— §4 把「loading the aggregate root」明列为留在 service 的职责;
  只有回调外的读侧构造才算 QueryService。

### 1.4 判层粒度:为什么不能按行判

抽边界类搬走的是**方法**,不是散行。实测第一刀 #1008 把 136 个 NCLOC 行搬进 `MembersQueryService`,
其中只有 27 行自带查询签名 —— 纯按行判会把另外 109 行记成「其他过程代码」,**系统性低估可搬**。
故判层分两遍:① 逐行取「最小可分类语句」的信号;② 无信号行**继承所属方法的主类**
(方法名信号计 2 票 —— 命名约定在本仓是规范,见 `architecture-boundary.md` §7)。
事务回调体内的无信号行**不继承**,恒记事务编排。

### 2.2 V2 members 三刀:主轴的唯一实证锚点

用「该刀**确实**从 `members.service.ts` 搬走的行」当带标签样本,在**搬走前**的文件上判层。
这条链路完整走事务上下文,是主轴的唯一实证验证。
(三刀 head 互为叠枝且前序刀产物逐字节相同,已核 `shasum` ⇒ 可逐刀隔离。)

| 刀 | 搬走 NCLOC | 判成「可搬」 | 判中目标类(细轴) | 误判成「不可搬」 |
|---|---|---|---|---|
| 第一刀 #1008 → QueryService | 136 | 119 = 87.5% | 92 = 67.6% | 3 |
| 第二刀 #1014 → AuditRecorder | 77 | 74 = 96.1% | 66 = 85.7% | 0 |
| 第三刀 #1015 → Presenter+Policy | 47 | 20 = 42.6% | 4 = 8.5% | 9 |
| **合计** | **260** | **213 = 81.9%** | — | **12 = 4.6%** |

**这张表的承重结论**:260 行**已被证明可搬**的代码里,分类器只把 **4.6%** 误判成「不可搬的事务编排」。
漏掉的 18.1% 落进「其他」四类,**不是**落进事务编排。
⇒ **仪器的偏向是低估可搬、不是高估可搬**;它在结构上**造不出**「增长主因是事务编排」这个结论。
本报告给出的可搬占比因此是**下界**。

### 2.3 敏感性上界

「收 `tx` 入参的 helper 是否整体算在事务边界内」是一处真判断分歧。打开该规则会让事务编排占比上升,
但它同时把 260 行已证可搬的代码误判 15.1%(远高于主口径的 4.6%)—— 已知偏保守、且方向相反。
故**主口径关闭该规则**,把它作为**敏感性上界**同时给出,让读数成为区间而非点估。

| 严口径 · 合计 | 可搬 | 事务编排 | 其他 |
|---|---|---|---|
| **主口径**(误判率 4.6%,取作结论) | **61.9%** | **18.5%** | 19.6% |
| 敏感性上界(误判率 15.1%,刻意悲观) | 42.1% | 40.7% | 17.2% |

**即便在刻意悲观、且已知误判率高 3 倍的上界下,可搬(42.1%)仍不低于事务编排(40.7%)。**

### 2.4 D1 抽样复核(回源码逐条读)

确定性抽样(按 sha 排序取固定位次),三组各回源码复核:

| 组 | 结果 |
|---|---|
| A 无偏 5 条 | 3 条判对;1 条(`registration-command.ts:519` 委托 `qualificationEvaluator.appendSnapshots` 判 Policy)**存疑** —— 它已委托给既有边界类,更像调用编排;1 条为 `Other:` 结构行,无争议 |
| B 定向 5 条(可搬 = 承重结论) | 4 条判对(Effect 通知入队 / Calculator 贡献值预填 / AuditRecorder / StateMachine);1 条(`activity-registrations.ts:1486`)同上存疑 |
| C 定向 3 条(事务编排) | 3 条全部判对(`tx.*.create` 写入 / `tx.attendanceSheet.update` 写入 / 锁获取) |

**复核当场抓到并已修的三个真缺陷**(修后重跑全部读数,本文所有数字均为修后)。
三个的方向**都利于本报告的结论**,不修就会高估可搬:

1. `ts.isStatement(Block)` 为真 ⇒ 上溯判层时把整个 `$transaction` 回调体当成「一条语句」,
   同一事务体内任意一处 audit 调用会把**全体兄弟语句**染成 AuditRecorder。
   实例:一次 `lockMembersForWrite()` 取锁被判成审计。修复后事务编排占比从 11.0% 升到 18.5%。
2. 事务内的读(`tx.x.findFirst`)未标记为「有信号」,会被方法主类顶掉。
3. **只认字面量 `$transaction(` 会漏掉具名事务包装器**(由 members 执行线的对拍读数暴露):
   本仓有 `runMemberLinearizedTransaction`(18 处)/ `runSingletonWriteWithUniqueRetry`(10)/
   `runOrganizationTopologyTransaction`(4)/ `runInTransaction`(2)共 34 处走包装器,
   `members.offboardCore`(170 NCLOC)整块因此被漏判。已改为通用判据:
   **任何实参回调的首参名为 `tx` 或类型为事务客户端的调用**都算事务边界开启点。

### 3.4 ⚠️ 「已经抽了很多,却仍是摩擦冠军」怎么解释

goal 点出的悖论确有其事,但数据给的解释与「抽边界无效」相反:

- `activities` 抽了 **23** 个边界类、`attendances` **11** 个、`activity-registrations` **6** 个 —— 全仓最多的三个;
- 它们同时是增长次数最多的三个(25 / 28 / 33)。

两者不矛盾:**抽出的量与增长的量都由业务活跃度驱动**。这三个域是本仓的业务主战场,
它们抽得多是因为长得多,不是因为抽了没用。真正的判据是**新增部分的构成**——
而新增部分里可搬仍占 58–74%,说明**边界抽取没有饱和**,不是「能抽的都抽完了、剩下的都是事务编排」。

反证在同一张表里:`members`(53.9%)与 `users`(76.0%)才是事务编排主导的形态,
而它们的事务编排占比**恰恰是全表最高的两个**,增长次数却排在热点之外。
⇒ 「事务编排主导」是一种**真实存在但当前不在热点上**的形态。

## 7. ⚠️ 附带发现:6-A 度量函数 `measureNcloc` 有缺陷

**本刀在复用立闸脚本的度量函数时发现,不在 goal 范围内,不在本刀修复,建议另行立项。**

### 7.1 缺陷

`scripts/check-codemap.ts` 的 `measureNcloc()` 用裸 `ts.createScanner` 循环剥注释,
遇到**带替换的模板串** `` `…${…}` `` 时未调用 `reScanTemplateToken()`,扫描器就此脱锁:
其后的文本被当作模板内容,**整行 `//` 注释不再被剥离,被计入 NCLOC**。

最小对照(可直接复跑):

| 输入 | `measureNcloc` | 真实代码行 |
|---|---|---|
| `const a = 1;` + 两行 `//` 注释 + `const b = 2;` | 2 | 2 ✓ |
| 同上,但首行改为 `` const a = `x`; ``(无替换) | 2 | 2 ✓ |
| 同上,但首行改为 `` const a = `${1}`; ``(有替换) | **4** | 2 ✗ |

实例:`recruitment-promotion.service.ts` 有 191 个整行 `//`,其中 **133 行被算成代码**。

另一条独立成因:`[...content]` 按**码点**建数组,而 `getTokenStart/End` 返回 **UTF-16 码元**偏移,
含非 BMP 字符(emoji)时索引错位 —— 已用合成样例复现。本仓 31 个基线文件暂未触发,但同属该函数的脆弱面。

### 7.2 影响面(实测)

| 项 | 读数 |
|---|---|
| 发现面文件总数 | 149 |
| 读数被抬高的文件 | **90 = 60.4%** |
| 31 个基线文件合计虚高 | **1746 行 = 5.0%** |
| **修正后跌破阈值 700 的基线文件** | **4 个** |

跌破阈值的四个(现口径 → 修正口径):
`activities/settlement-submit.service.ts` 789 → **628** ·
`recruitment/recruitment-promotion.service.ts` 817 → **682** ·
`activities/ledger-posting.service.ts` 751 → **659** ·
`notifications/notification.service.ts` 706 → **644**。

反向检查:现口径未入基线、但修正后 ≥700 的文件 —— **空**。故缺陷是**单向虚高**,不会漏收。

### 7.3 对既有结论的影响

| 结论 | 现口径 | 修正口径 | 是否改变 |
|---|---|---|---|
| 摩擦(宽) | 182 | 176 | 否 |

⇒ 立闸报告 §3 / §4 的**判断不受影响**,但基线的**成员集合**有 4 个假阳性。
本文全部归因读数均基于**修正口径**(判层掩码改为用 parser 收集真实 token 区间,不依赖手工 rescan)。

### 7.4 建议

按缺陷类棘轮范式处理:修 `measureNcloc` 一处即修全类(`service-loc-*` 与尺寸棘轮共用同一份计算),

现有 22 条尺寸段对照里没有这一条,所以缺陷十一次都没响。
修复会改动 `scripts/**` 与 `harness/**`(基线需重算),**属红区,须维护者授权**,不在本刀写集。
