「**功能没做**」推到了「**只缺证据**」。本刀**一行业务实现都没动** —— 只写测试 + 收窄卡点文本。

#### 逐条:验的是合同哪一句、断言怎么覆盖每一格

⭐ **AC-064**「7天归档等待结束后可以归档，但合法更正不因7天过去而被永久禁止。」

后半句既有(关账 spec ⑥「归档等待期早已过去 ⇒ 让位后重新关账照样成功」);
前半句此前**只有纯函数判据**,归档 spec 自己在文件头如实写着「结算路径的放行那一半没有 HTTP 证据」。
本刀按那段卡点点名的做法,在 `activity-settlement-closure.e2e-spec.ts` 里**接续链**
(而不是把整套关账夹具复制进归档 spec —— 那条链要一条真 `ActivitySettlementClosureRevision`,
它有三条必填外键)。四格**各自成 `it`**:

| 用例                                               | 少了它,什么样的坏实现也能全绿 |
| -------------------------------------------------- | ----------------------------- |
| 关账已过 7 天 ⇒ 归档放行(200,`reasonCode=settled`) | 「永远拒」                    |
| 关账当刻(等待期 7 天)⇒ 20157 且归档六列一列没写    | 「关过账就放行」              |
| 只差 2 小时不满 7 天 ⇒ 仍是 20157                  | 「阈值取多大都行」            |
| `archiveWaitingDays=0` ⇒ 当刻即可归档              | 「把 7 写成常量」             |

⚠️ 时间口径:本组**不能**沿用别处的 2020 年固定时刻 —— 等待期是拿**同事务 `now()`** 与
`closedAt` 比的,所以「时间过去了」只能靠把 `closedAt` 往回拨造,而**回拨基准也取 DB 的 `now()`**
(容器与宿主时钟不一定同步,差几秒就会把「差 2 小时」那格的余量吃掉)。回拨量取 7 天 ± 小时级,
与墙钟无耦合、无定时炸弹。回拨后先断言「受影响行数恰为 1」—— 先验仪器,再下结论。

⭐ **AC-066**「发布通知可以选择目标组织、标签或明确不广播；取消、改期等事件冻结收件人后异步展开。」

前半句三个可选项各自已有判据(组织 → `activity-recipient-freeze.spec.ts` ⑥;标签与「明确不广播」
→ 冻结 e2e 既有两条);后半句点名**两个**事件,取消由 ADV-016 钉住,而**改期**此前 `test/` 下零绑定。
本刀补三格,各自成 `it`:

- **集合**:改期 intent 的收件人恰为改期那一刻的在册报名者;反面样本是**同一场活动、同样报过名、
  只有「已退出(cancelled + 软删)」这一点不同**的人 —— 在被测那一维上单独不同,上层边界遮蔽不了它。
- **异步展开**:intent 形成后真改名单(一人退出、一人新报名),抽干 outbox,实收集合与快照**逐字相同**
  —— 退出者仍收到、后到者收不到。**先钉两边非空,再比集合**(空集 == 空集是本仓栽过的假绿形状)。
- **盖章**:改期批 `basisKind=registration-roster`、`basisRef=['schedule:<updatedAt>']`、
  `cohortKey=activity-change:<活动>:<updatedAt>`,与发布批是两个 cohort、互不吞并。

⭐ **ADV-022**「更正提交或生效与关账、归档同时发生。」—— 它是一张 2×2 的表:

|              | 关账                         | 归档     |
| ------------ | ---------------------------- | -------- |
| 更正**生效** | AC-063 并发 spec ②(**既有**) | ⑤-a 本刀 |
| 更正**提交** | ⑤-b 本刀                     | ⑤-c 本刀 |

另加 ⑤-d「归档 × 关账」:归档取的是与关账 / 终审 / 更正**同一把** Activity `FOR UPDATE`,
这条接缝是归档刀(2026-08-25)新造的,此前全仓零并发用例。四条都用**两套 app / 两套 pool**,
并用 `pg_stat_activity` 的 `wait_event_type='Lock'` **正面数出锁等待者**(数不到就抛,
「没成功」不等于「排过队」),轮询上限压到 2.5s 以免把真症状变成超时假红。

🔴 三条做成**判决翻转**,而不是「反正只有一个成功」(后者在**完全没有锁**的实现上也常常是绿的):

- **⑤-a**(更正 commit × 归档):入口世界里 active closure 还挂着、等待期已过 ⇒ **锁前判必然放行**;
  实际拿到 20156 ⇒ 只可能是锁后重读了 closure。
- **⑤-b**(更正 submit × 关账):入口世界里 run 还是 `posted`、零开放更正 ⇒ **锁前判八类全过**;
  实际被 `pending_work_exists`(`pendingCorrection: 1`)挡下。附正对照:把该更正驳回后关账成功
  —— 证明那条 blocked 不是「这个夹具本来就关不了账」。
- **⑤-d**(关账 × 归档):入口世界里一张 active closure 都没有 ⇒ **锁前判必然 20156**;
  实际放行且 `reasonCode=settled`。

⑤-c 不是判决翻转(更正提交不看活动状态,归档也不看在飞的更正),读数是另外三组:屏障 +
归档赢家效果落地 + 🔴 **更正在活动已 `archived` 之后照样提交成功** —— 这正是 AC-064 后半句
「合法更正不被永久禁止」在归档这一侧的读数。

🔴 **每一维各自成 `it`**:jest 在一个 `it` 内首个失败即停,塞一起会让后面的断言从未被执行,
而这在基线全绿时完全看不出来(`docs/ai-harness/TOOL_TRAPS.md` §6.1)。
